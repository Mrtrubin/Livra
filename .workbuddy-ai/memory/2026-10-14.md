## 优化：请求详情页对齐 Chrome DevTools Network

- **响应体缓存不能挂在 request 对象上**：后台每次 publish 都推送新对象，panel 侧的引用会被整体替换。改用独立的 `bodyCache`（key → state）。

## 侧边栏改成按标签页 + 单标签页调试 + 抓跨站 iframe

用户反馈：点一次图标所有标签页都出现侧边栏、每条标签页都弹「正在调试此浏览器」。

**根因**：`chrome.sidePanel.setPanelBehavior({openPanelOnActionClick: true})` 等价于 `open({windowId})`，
官方示例注释写明 `open({windowId})` 会 "open the panel in all the pages on the current window"；
**只有 `open({tabId})` 才是按标签页的**。

**改法**（对齐官方 cookbook.sidepanel-open / site-specific 两个示例）：
- `setPanelBehavior({openPanelOnActionClick: false})` + 全局 `setOptions({enabled:false})`
  → 没主动打开过的标签页一律不显示侧边栏
- `chrome.action.onClicked` → `setOptions({tabId, path, enabled:true})` + `open({tabId})`
  → 只为点图标的那个标签页开
- `startListening` 里先 `stopListening` 掉其它标签页 → 同时只有一个调试会话，不会叠加多条调试提示
- 面板用 `chrome.windows.getCurrent()` 拿到自己的 windowId 传给 `GET_STATE`；
  **service worker 里没有「当前窗口」概念，不能用 `lastFocusedWindow`**（多窗口会串）
- `tabs.onActivated` 里按 windowId 过滤

**注意**：那条「已开始调试此浏览器」是 Chrome 给 `chrome.debugger` 的内置安全提示，
文案和显示范围都由 Chrome 决定，扩展无法自定义/关闭；唯一办法是启动 Chrome 时加
`--silent-debugger-extension-api`（仅开发自用可行）。能做的就是保证只有一个调试会话。

**抓跨站 iframe / Worker**：加 `Target.setAutoAttach({autoAttach:true, waitForDebuggerOnStart:false, flatten:true, filter:[iframe/worker/shared_worker/service_worker]})`，
在 `Target.attachedToTarget` 里对子会话单独 `Network.enable`。
实测：改之前 iframe 里的 `/api/b` 完全抓不到，改之后能抓到，且 `targetType:"iframe"`。

**关键坑**：**`requestId` 只在单个 CDP 会话内唯一**，子会话是独立会话，会和主会话撞 key。
所有 request 相关 map 的 key 必须带上 `sessionId`（`requestMapKey(tabId, sessionId, requestId)`），
`GET_RESPONSE_BODY` 也要用带 sessionId 的 target 去取。
另外子 target 刚 attach 时 `targetInfo.url` 是空的，退回用该请求自己的 `documentURL` 补来源地址。

**验证**：`/tmp/cs-test/harness6.js`。结果：
- `getOptions` 全局 `enabled:false`、打开过的标签页 `enabled:true`、其它标签页 `enabled:false`
- iframe 的 `/api/b` 抓到了，列表里带「跨站 iframe」紫色 chip，详情页「常规」多一行「来源」
- 在标签页 A 开监听后 attachedTabs=[A]，切到 B 再开监听后 attachedTabs=[B]（A 自动停）

## 修：`sidePanel.open()` may only be called in response to a user gesture

**原因**：`action.onClicked` 里先 `await chrome.sidePanel.setOptions(...)` 再 `await chrome.sidePanel.open(...)`。
**`open()` 依赖用户手势，中间只要 await 过任何 API，手势就失效**。
（Edge 的 microsoft/MicrosoftEdge-Extensions#142 里官方回复确认：`open()` 只能在用户手势里调用，
`tabs.onActivated` 这类非用户交互的时机调用必然报这个错。）

**改法**：两条调用放进**同一个同步块**，`setOptions` 在前、`open` 在后，谁都不 await。

```js
chrome.action.onClicked.addListener(tab => {
  chrome.sidePanel.setOptions({ tabId: tab.id, path: PANEL_PATH, enabled: true }).catch(() => {});
  chrome.sidePanel.open({ tabId: tab.id }).catch(err => console.error("打开侧边栏失败", err));
});
```

**为什么 setOptions 放前面也行**：两条消息走同一个 IPC 通道，浏览器按顺序处理，
`open()` 真正执行时该标签页已经 enabled。而且官方 cookbook.sidepanel-open 示例本身就是
`open()` 在 `setOptions()` 之前调用的 —— 说明 `open()` 并不要求 `enabled` 已经为 true，
所以正反两种顺序都成立，这里选 setOptions 在前更稳。

**验证限制**：headless 里没法验证手势路径 —— CDP `Runtime.evaluate({userGesture:true})` 设置的是
页面的 user activation，**不会**传播到扩展 API 的手势检查，所以 A/B/C/D/E 五种写法在
`/tmp/cs-test/harness7.js` 里全部报同一个手势错误，无法区分。只能靠真机点图标验证。

## 调研：用 CDP Fetch 域做「正则改写响应体」（已实测跑通）

需求：拦截请求，响应内容命中正则就替换后再交给前端。

**MV3 里只有 CDP Fetch 域能做到**：`chrome.webRequest` 的 blocking 能力被砍；
`declarativeNetRequest` 只能改 URL/请求头、碰不到 body；注入脚本 patch `fetch`/`XHR` 只能覆盖
页面 JS 发的请求，文档/脚本/图片/CSS 都拦不到且可被检测。

**链路**（`/tmp/cs-test/harness8.js` 实测）：
`Fetch.enable({patterns:[{urlPattern:'*', requestStage:'Response'}]})`
→ 每条响应触发 `Fetch.requestPaused`（**页面此时是挂起等待的**）
→ `Fetch.getResponseBody` 取正文 → 正则替换 → `Fetch.fulfillRequest` 回填；
不命中就 `Fetch.continueRequest` 放行。

**实测结果**：
- gzip 压缩的 JSON 响应 → 页面收到改写后的内容 ✓
- 未压缩的纯文本 JSON → 同样改写成功 ✓
- 不命中规则的请求 → 原样返回，未被改动 ✓

**踩到的坑（都有实测依据）**：
- **`Fetch.getResponseBody` 的 `base64Encoded` 对纯文本 JSON 也常常是 `true`**，
  所以**不能拿它判断"是不是二进制"** —— 第一版就是这么写的，结果所有响应都被当成二进制放行了。
  要改成：base64 解出来 → 按 `content-type` 判断是否文本（json/js/xml/text/charset）→ 再决定处理。
- **拿到的 body 已经是解压后的**（实测 gzip 响应解出来的字节是 `7b226e61` = `{"na`，不是 `1f8b`），
  所以回填时**必须删掉 `content-encoding` 并重算 `content-length`**，否则浏览器按 gzip 去解压明文会炸。
- `Fetch.fulfillRequest` 的 `body` 必须是 base64；中文要 UTF-8 编码后再 base64（不能直接 `btoa`）。
- **每一条 `requestPaused` 都必须回应**（continue/fulfill/fail 三选一），漏一条页面永久卡住。
- 带 `/g` 的正则 `test()` 有 `lastIndex` 状态，连续调用会漏匹配，用前要 `lastIndex = 0`。
- 跨站 iframe / Worker 是独立会话，`Fetch.enable` 也得在子会话上各调一次。

## 踩坑：在 `Fetch.requestPaused` 的 if 条件里按 URL 过滤会卡死页面

用户把 `background.js` 的 `Fetch.requestPaused` 分支改成了：

```js
const isTargetUrl = url.includes("config");
if (method === "Fetch.requestPaused" && isTargetUrl) { ... }
```

结果页面卡死；把 `&& isTargetUrl` 注释掉就正常。

**原因**：`Fetch.requestPaused` 是**必须应答**的事件 —— 每条被挂起的请求都必须在
`continueRequest` / `fulfillRequest` / `failRequest` 里选一个回应。
在 `if` 里按 URL 过滤，等于把不匹配的请求**丢弃**了：没人回应 → 该请求永久挂起 → 页面一直等它 → 卡死。
注释掉过滤后，每条请求都会进入分支并走 `continueRequest`，所以不卡。

**正确做法**：过滤只能放在「应答之后」或「更外层」：
1. 收窄 `Fetch.enable` 的 `patterns[].urlPattern`（CDP 层，不匹配的请求压根不会被暂停，最省性能）
2. 或设 `REWRITE_RULES[].urlPattern`（规则层，`handleRequestPaused` 内部会 `continueRequest` 放行不匹配的）

**最小复现**：`/tmp/cs-test/harness9.js`，`MODE=filter` 复现挂起、`MODE=all` 正常：
```
MODE=filter:  被挂起 ["/app.js","/other.js"]  已回应 ["/app.js"]      /other.js -> TIMEOUT
MODE=all:     被挂起 ["/app.js","/other.js"]  已回应 ["/app.js","/other.js"]  /other.js -> ok
```

## 踩坑：Fetch 域拦不到「缓存命中」的响应（cn.vuejs.org 真实案例）

**现象**：规则明明匹配（直接调 `applyRewriteRules` 返回 hits），但在 cn.vuejs.org 上
`config.DHyWUa4I.js` 始终 `rewritten: false`，而且 service worker 里 **`Fetch.requestPaused` 一条都没触发**。

**根因**：**`Fetch` 域不会拦截由 HTTP 缓存直接满足的响应。**
cn.vuejs.org 的资源带 `cache-control: max-age=31536000, immutable`，第二次访问所有 chunk 都从磁盘缓存出，
`Fetch.requestPaused` 根本不触发 → 改写无从谈起。

**决定性隔离**（`/tmp/cs-test/harness13.js`，纯 CDP 不带扩展）：
```
① Fetch.enable，不关缓存            → 拦到 10 条，config chunk 不在其中
② + Network.setCacheDisabled(true)  → 拦到 28 条，config chunk 抓到了
```

**修法**：开改写时必须同时 `Network.setCacheDisabled({ cacheDisabled: true })`
（DevTools 的 "Disable cache" 复选框做的就是这件事）。已加进 `rewrite.js` 的
`disableCacheForRewrite()`，在 `startListening` 和子会话 attach 时各调一次。

**排查过程中绕的弯路**（记下来免得重走）：
- 先怀疑缓存 → 用 harness10 连发 3 次同一 URL 全被改写、`fromDiskCache` 全 false，**误判缓存无关**。
  其实那是因为跨域 fetch + Fetch 域已开启，跟真实站点的「页面自己的 chunk」场景不同。
- 又怀疑 `Target.setAutoAttach(flatten)` 和 Fetch 域冲突 → 用 `NO_AUTOATTACH=1` 空操作验证，**排除**。
- 最后用「纯 CDP 不带扩展」隔离，才定位到缓存。

**测试也要跟着改**：`test/rewrite-extension.js` 的 fixture 之前是 `cache-control: no-store`，
所以永远测不出这个坑。已改成 `max-age=31536000, immutable`（测试流程本来就加载页面两次，
第二次就是缓存命中），并把 fixture 路径改成 `/assets/chunks/config.DHyWUa4I.js`
以匹配收窄后的 `FETCH_PATTERNS = "*config*"`。

## 需求：修好发弹幕 + 写调试桥

**最终定位出 4 个真 bug**（前三个叠加才造成「点了没反应、也没报错」）：

1. **隔离世界只共享 DOM，不共享 window 上的属性**（根因）。
   `window.__livraLive` 在 main world 里是对象，在 content script 里是 `undefined`。
   所以 `sendDanmaku` 从来没被调用过 —— 而它的分支里没有返回，等于静默失败。
2. **发送结果文案会被直播数据刷掉**：发送状态写在 `#liveHint`，而 `renderLive()` 每次收到消息

3. **页面失焦时回车被忽略**：`document.hasFocus()===false` 时合成 Enter 完全不触发发送
   （表现为字塞进去了、什么都没发生）。浏览器窗口不在前台就会这样。
4. **多个 content script 实例重复处理**：manifest 注入 + SW 补注入并存时，
   `tabs.sendMessage` 发给所有实例 → 文本被插入输入框两次、发出去是重复的。

**正确的发弹幕做法**（实测可用）：驱动页面自己的输入框，不自造请求。
